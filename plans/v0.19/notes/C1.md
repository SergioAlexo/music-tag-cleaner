# C1 - DJ playlists (Rekordbox / Mixxx / Music Tag Cleaner), smart playlists, genre export

Branch `worktree-agent-ae3d361f81622ff75`. No settings change (settings stay at 21; the Rekordbox/Mixxx location overrides live in `localStorage` keys `playlists.path.<source>` / `playlists.source`, so no v22 step was needed).

## Decisions (coordinator overrides applied)
- **SQLCipher in pure Rust** (`commands/sqlcipher.rs`; crates `aes`, `cbc`, `hmac`, `sha2`, `pbkdf2`). `rusqlite` features are unchanged (`bundled`). `master.db` is decrypted page by page (PBKDF2-HMAC-SHA512 256000 iters, 4096-byte pages, 80-byte reserve, **every page's HMAC-SHA512 verified**) into a temp plain SQLite file, read with the existing rusqlite, and the temp file is deleted (drop guard). The live file is only read, never opened by SQLite, never written. The passphrase is the published constant from pyrekordbox (same on every install). Dev/test builds optimise just the crypto crates (`[profile.dev.package.*] opt-level = 3`) because the KDF is far too slow unoptimised.
- **Rekordbox writes = rekordbox.xml only.** Direct master.db writing (re-encrypt + `localUpdateCount` USN + `masterPlaylists6.xml`) is **out of scope; follow-up**. XML has no smart-playlist element, so smart lists export as static playlists of their current members; the UI says so (Copy menu hint, success toast, dialog text).
- **Mixxx writes direct** to `mixxxdb.sqlite`: process check (`tasklist`/`pgrep`, no new crate), timestamped backup `mixxxdb.sqlite.mtc-backup-YYYYMMDD-HHMMSS` (newest 10 kept), ONE transaction, UI confirm once per page session. Smart lists = static crates named `[smart] <name>`, rebuilt by upsert.
- **Bug found by the real-schema test:** rusqlite's bundled SQLite turns foreign keys ON by default, and Mixxx's FKs point at the stale `library_old` table, so every insert failed with "no such table: main.library_old". `apply_ops` sets `PRAGMA foreign_keys = OFF` explicitly.

## Unverified / follow-ups
- Rekordbox numeric smart-rule encodings (bpm / rating / key / date value units) are from pyrekordbox, never seen on 7.2.19. Evaluation of such lists is best effort; ask the owner to create one of each and re-read `SmartList`.
- `buildRekordboxSmartList` (rules -> SmartList XML) is tested but not used: nothing writes master.db. Follow-up: master.db writer (re-encrypt, USN, masterPlaylists6.xml), then smart lists could be real.
- Reading while Rekordbox runs uses whatever is in `master.db` (a `-wal` isn't applied); a torn read fails the HMAC check with a "close Rekordbox and retry" message.
- Mixxx smart crates keep no rules in Mixxx; the rules live in the MTC smart playlist of the same name. Renaming one side breaks the link.
- Albums in the facet export merge same-named albums by different artists.

3. Copy a Rekordbox playlist to Music Tag Cleaner; "N not in your Library" count/list; Load as session opens a new Library tab.
4. Copy to -> Rekordbox (xml file)...: save; import it in Rekordbox's xml view.
5. Mixxx tab (closed): Copy a playlist to Mixxx playlist and as crate; a `mixxxdb.sqlite.mtc-backup-*` appears; open Mixxx, check them. With Mixxx open, writes are disabled with a message.
6. "Smart playlists from genres...": tick a few genres, targets MTC (+Mixxx/xml), run twice: second run says "updated", no duplicates.
7. MTC smart playlist: Rules, change a rule, live count updates, Save; Refresh re-evaluates; "Push smart lists to Mixxx".
