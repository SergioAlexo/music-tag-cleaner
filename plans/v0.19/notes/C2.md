# C2 - Rekordbox <-> Mixxx sync

Settings v24 (`djSync`: directions per item, Mixxx target, master, relocate, onStart).

## Decisions
- **UI home: a dialog opened from the Playlists page** ("Sync Rekordbox <-> Mixxx..."), not a Settings card: the preview is a big interactive list (counts, expandable lists, conflicts) that sits next to the playlist trees it changes. Options live in the dialog and persist in settings v24. No SettingsPage edit.
- **Engine in TypeScript** (`src/lib/djSync.ts`), not Rust: Rekordbox smart playlists have no stored members (only `smartRules.ts` can materialize them) and `djPlaylists.ts` already builds the rekordbox.xml. Rust (`commands/dj_sync.rs`) owns reads, snapshot storage, Mixxx writes, B4 map reading. No second db layer: it calls C1's `rekordbox_db` / `mixxx_db`.
- **Rekordbox is read-only.** Rekordbox-bound changes go to a generated rekordbox.xml (dialog says so). They stay *pending* (bases not advanced) and keep being offered until Rekordbox shows them, then settle on their own.
- **Mixxx writes** reuse C1's backup + single transaction: `mixxx_db::apply_ops_with` runs relocations, playlist ops and metadata in the same transaction. Refuses while Mixxx runs.
- **State** = JSON blob per side in new table `dj_sync_state` of the MTC library-index sqlite (created lazily; no index version bump). Tagged with the Mixxx target (playlist/crate): switching target means "first sync" (which never deletes).
- **Diff** is "side vs its own last-synced base", never "side vs side". Both changed + different = conflict (user picks per conflict; unresolved = left alone). First sync: nothing deleted, same-name differing lists = conflict, metadata: blanks filled, otherwise master wins. Play counts: max. Renames detected (same members under a new name). One-way direction: the source wins, other side's edits ignored.
- Folders: Mixxx has none, so a Rekordbox folder path becomes the list name `Folder / Sub / Name`; the reverse splits on ` / ` into xml folders. Empty folders are not synced. Rekordbox smart lists are materialized (read-only: nothing flows into them); ones with unevaluable rules (My Tag) are skipped and counted. Mixxx `[smart]` crates (C1's pushed MTC smart lists) are excluded.
- **Metadata**: bpm, key, rating, plays, comment, colour. Never beatgrids/cues (future work: map via the existing `rekordbox_import.rs` cue import). BPM is never written over a Mixxx beat grid (grid owns it; counted as "grid-locked", not re-offered). Key writes Mixxx's `key`, `key_id` and the `KeyMap` protobuf blob (format verified against the owner's rows, byte-identical in a test). Colour: Rekordbox ColorID 1-8 <-> fixed RGB table (xml spec values); Mixxx colours outside it are not pushed... (they are written to xml as given; Rekordbox may ignore non-palette colours).
- **Moved files (B4)**: all `move-maps/*.csv` are chained into canonical keys, so a file moved on disk matches on both sides while either program still holds the old path. Optional "point Mixxx at moved files" updates `track_locations` (only if the new file exists and Mixxx has no track there). Rekordbox must be relocated by the owner in Rekordbox.
- Triggers: manual dialog; optional check at app start (settings `djSync.onStart`) that only toasts counts, never applies. No daemon.
- Actions: `djsync.preview` (readOnly), `djsync.apply` (`dangerous`, conflicts left alone, optional `xmlPath`).

## Dry run on COPIES of the live dbs (master.db 4405 tracks, mixxxdb 5480 tracks; apps not running)
First sync, default-ish options (playlists both ways, bpm/key Rekordbox->Mixxx, rating/plays/comment/colour both):
- Rekordbox side: 217 lists (2 smart skipped: unevaluable), Mixxx side: 0 playlists. 843 tracks in only one library (not compared).
- To Mixxx: 217 playlists created; BPM 3444, key 2844, rating 260, play count 1184, colour 65 track updates (3530 tracks touched). 30 BPMs left to Mixxx beat grids.
- To Rekordbox (xml): 215 comments, 6 play counts; xml with 221 track updates, 63 KB. Conflicts: 0.
- Applied the Mixxx part to the Mixxx copy via `apply_ops_with`: 217 ops, 0 unmatched paths, 3530 tracks, `integrity_check` ok.
- **Second run against the changed copy: 0 Mixxx-bound lists, 0 Mixxx-bound metadata, 0 conflicts** (idempotent). The 221 Rekordbox-bound updates remain offered until imported, as designed.
Reproduce: copy both dbs to a scratch dir, `MTC_SYNC_DRYRUN_DIR=<dir>`, run `cargo test dryrun_1 -- --ignored`, `npx vitest run src/lib/djSync.dryrun.test.ts`, `cargo test dryrun_2 -- --ignored`, vitest again (all skipped when the variable is unset).

## Tests
- TS `djSync.test.ts` (23): first sync, add/remove/reorder/rename, conflicts + picks, delete-vs-edit, one-way, smart lists, unmatched/extra members, crates as sets, idempotency (lists + metadata + rename; pending-until-imported; unticked item re-offered), metadata rules (fill, master, max plays, conflict, grid lock, key/BPM equivalence), move maps and relocation, xml tree.
- Rust `dj_sync` (6 + 2 ignored dry runs): key mapping and KeyMap blob, metadata writes incl. grid guard and clearing, relocation (success, clash, missing file), state round trip, CSV maps.

## Not verified / left
- UI never run (`npm run tauri dev` needed). A real Rekordbox import of the generated xml: unknown whether it updates metadata of tracks it already has (playlists import fine per C1); the dialog states the xml is imported by hand.
- Mixxx launch against a synced db not tried; Mixxx may re-derive BPM/key from its blobs on rescan.
- Rating/BPM semantic differences: Mixxx BPM tolerance 0.05 for equality.
- Master.db writing (so Rekordbox changes needn't go via xml) is still the C1 follow-up. Deletions bound for Rekordbox cannot be expressed in xml (listed, not exported).
- Future: beatgrid/cue sync.

## Click-through (Mixxx CLOSED, throwaway-safe: a backup `mixxxdb.sqlite.mtc-backup-*` is made)
1. Playlists > "Sync Rekordbox <-> Mixxx...": both libraries read; first-sync notice; table of items with counts. Expand Playlists / BPM: lists with checkboxes.
2. Untick a group and a single playlist, Apply: Mixxx gets the rest (open Mixxx to check playlists, ratings, keys), a Save dialog appears only if Rekordbox-bound changes exist; import that xml in Rekordbox.
3. Reopen the dialog: Mixxx-bound counts are 0; Rekordbox-bound remain until imported.
4. Change a rating in Rekordbox and a different one in Mixxx for the same track, reopen: a conflict row with radios; "Rekordbox wins all", Apply.
5. Rename a Rekordbox playlist, reopen: shows as rename, not delete+create. Switch "Playlists in Mixxx become" to Crates: first-sync notice again.
6. With Mixxx open: banner, Apply disabled for Mixxx-bound changes. "Forget sync history" resets.
7. Settings option "Check for changes when the app starts" then restart: toast with counts.
8. After "Move to collection...": tracks still match; tick "Point Mixxx at moved files".
